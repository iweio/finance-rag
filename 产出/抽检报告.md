## 判定口径修正：页码会落在条文中间

首轮比对时 `BSE-001-5.2.10` 报了不一致，差 19 字。定位后是原始 PDF **在这条条文中间换页**，原始区间里夹着一个页码 `-71-`，被清洗规则 2 正确删掉了——chunk 更短是对的。归一里补上「去页码」后逐字一致。

**这条值得记一笔**：页码并不总在页边界上，它可能落在一条条文内部。清洗规则 2 因此不能只按「整行是页码」在页级别匹配（当前实现是按行匹配全文，写法是对的）。本次 20 条里命中 1 次，全库比例未测。

## 附：`NFRA-016` 全量抽检（2026-10-27）

`NFRA-016` 与其余 158 份**不是同一类来源**（是 `脚本/_fetch_nfra016.py` 把 gov.cn 页面上
内联的正文**转**成的 `.docx`，不是下载的原件，见 [契约/README.md](../契约/README.md) §4 #15）。
**正因为来源不同类，它不能只做 20 条抽样 —— 全量 207 条都对了。**

判据与上面 20 条相同（chunk 文本须逐字落在**它自己那一条的原始区间内**），
但**对照材料换成了采集时缓存的 gov.cn 原始页面** `产出/_fetch/gov1.html`：

```bash
python 产出/_fetch/spotcheck_nfra016.py
# 区间划出 206 条；NFRA-016 207 个 chunk 中：逐字落在自己区间内 207，不在 0
```

**不拿转出来的 `.docx` 当对照** —— 那等于自证。用页面原文才是独立的一份材料。

**划区间时踩到一个坑，值得记：不能按「条号的首次出现」划。** 该办法正文里有**前向援引**：

```
(二)第二档商业银行应按照本办法第六十五条第五款、第六十六条第二款、第六十七条第二款、
    第六十八条第三款、第六十九条第三款、第七十一条第三款、第七十二条第三款、…
```

七八个条号挤在同一句里、彼此只隔 9 个字符，按首次出现划出来的区间全塌成空。
正确判据是**只有段首的 `第X条` 才算条标题**（生产侧 `_kb.anchor_spans` 用的也是行首判据）。
`_verify.py` 第 15 项跑出来 206 个锚点、撞车 0，说明生产侧这条判据本身是对的 ——
是这次**写抽检脚本的人**默认了「援引只会向后指」，把前向援引漏了。
