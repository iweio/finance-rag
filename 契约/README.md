## 1. 三个 ID 是全系统的骨架

三条链路都靠 ID 串起来，任何一条断了溯源就断。生成规则见 [SPEC.md](SPEC.md) §2.1 / §2.2。

```
doc_id     = {机构代码}-{三位流水号}          例：PBC-001
clause_id  = {doc_id}-{原文锚点}              例：PBC-001-A53
             ├ 第五十三条  → A53
             ├ 三、        → S3
             └ 3.6.2       → 3.6.2
```

`clause_id` 是 Milvus 主键、是 `/api/v1/clause/{clause_id}` 的路径参数、是前端溯源卡片的锚。
所以**第 4 周冻结之后不许再改**：改一次，Milvus 全库重写 + P1 查询侧 + P3 前端 + 评测集全返工。

### 4.1 新增一份文件时，生成器会怎么坑你（本轮实测）

`_meta.py` 与 `_kb.py` 是按当时的语料写的，**新文件的形状稍有不同就会踩到没覆盖的分支**。
本轮加 `NFRA-016` 一共踩了三个，都不报错 —— 记在这里，下次加文件照着查：

**① `doc_id` 绝对不能重跑 `_meta.py`。** 它按**目录遍历顺序**发流水号
（`seq_by_code = Counter()`），重跑会把已有 158 行的 `doc_id` 全部重排；而且会**抹掉
`source_url` / `topic_tags` 两列**（`_meta.py:681` 有告警）。所以新行是**手工追加**的
（`产出/_fetch/add_nfra016_row.py`），`source_dir` 从相邻行取、不手打路径。

**② 文件名里不能带 `令YYYY年第N号` 这种文号。** `_meta.parse_std` 的 `HW` 只认 `〔Y〕`
写法，认不出就把整串当**机关名**塞进 `org`，下一句 `AGENCY_CODE[first_agency(org)]`
直接 `KeyError`。**没有去扩 `HW`** —— 它同时驱动目录 3 的解析（73 行），为一个新文件动它会
波及存量，性质与 #11 那次「按自己的约定改 4 行」相同。改法是**把文件名里的文号去掉**，
让 `parse_std` 返回空、再走「正文优先于文件名」的正常路径。

**③ 沿革行同时印公布日和施行日时，`publish_date` 会取到施行日。**
判据本来只有「头部最后一个日期 = 公布日」，这条在令头文件上成立，但写法
`(2023年10月26日…令2023年第4号公布 自2024年1月1日起施行)` 里**最后一个日期是施行日**。
给 `dates_from_body` 打了补丁（新增 `_is_effective_at`，按前后缀「自/于/从 … 起/施行」判）。
补丁让 8 行自动落到正确值上 —— **反过来说明它们本来错着**（就是 #9 的第二轮）。

**④ 补丁同时给另外 4 行换了另一个错值，没有修好。** 说清楚免得下次重新踩：

| 文件 | 打补丁后取到 | 为什么 |
|---|---|---|
| `PBC-036` / `PBC-037` | **会议通过日** | 人行令头部印的是「…会议通过」，公布日在**文末汉字数字落款**里（阿拉伯数字形态扫不到）。已按 #9 第二轮手工改正 |
| `PBC-071` | **会议通过日** | 同上，未改（现值 `20040412` 是上一轮按落款改对的） |
| `SPC-001` | **所援引法释〔2019〕9号的通过日** | 头部有援引件的日期。已按 #9 第二轮手工改正 |

**结论：补丁留着，但别指望它「跑一遍就全对」。** 它让生成器能复现 8 个已人工核过的值，
方向是对的；剩下 4 行是**另一个 bug**（落款在文末 + 援引件日期），不在这条补丁的射程里。
**冻结的是表，不是生成器** —— `_verify.py` 校验的是表，表是人工改正后的结果，
所以这 4 行不影响任何门禁，但**下次重跑 `_meta.py` 会把它们再弄错一次**（而重跑本来就被 ① 禁止）。

> 与 [SPEC.md](SPEC.md) §8.3「在场 ≠ 正确」是同一个坑的**第七次**。这一次的新形态是：
> **一次修复可以同时修对一批、修错另一批** —— 所以补丁跑完必须**逐行核对**，
> 不能只看「改了几行」。

## 5. 契约之间怎么对齐

字段名在四处出现，必须逐字符一致：

```
SPEC.md  §2 列定义  ──┐
                      ├─→  语料元数据.xlsx 的列名
_meta.py / _verify.py ┘

SPEC.md  §2 列定义  ──┬─→  Milvus finance_clause 标量字段名   （DB.md §3）
                      └─→  MySQL 表列名                      （DB.md §2）
                              └─→  API 响应字段名             （API.md）
                                      └─→  RagEngine 返回模型  （MODULE.md）
```

一处改名要跟着改：`SPEC.md` → `脚本/_meta.py` → `脚本/_verify.py` → `DB.md` → `API.md` → `MODULE.md`，最后重跑两个脚本，**全过才算改完**：

```bash
python 脚本/_verify.py           # SPEC §6 的 15 项语料校验
python 脚本/_contract_check.py   # 13 项契约交叉校验
```

`_contract_check.py` 就是防「API 字段名与 DB 列名不一致」这类历史高发 Bug 的。它按上面的箭头逐个比对，任何一条链断了都会 FAIL。
