## 1. 范围

本 Spec 约束 `语料元数据.xlsx`（sheet 名 `语料元数据`）的列定义。该表是 P2 交付给 P1/P3 的
数据契约：

- **P1（RAG 核心）** 按 `clause_scheme` 决定切分锚点，按 `doc_id` + 原文锚点拼 `clause_id`（§2.2）。
- **P3（溯源卡片）** 按 `/api/v1/clause/{clause_id}` 取卡片，用 `doc_title` / `org` / `doc_number` /
  `status` / `effective_date` 渲染。

**收录范围：只收 `有效文件` 目录下的文件。** `旧版(已被修订)`、`失效`、`废止`、`废止及失效`、
`8.重复文件` 一律不入表。共 **159 份**。

例外：`status` 允许非 `有效`（§5.4）。文件的物理位置由 P2 决定后即冻结，不因时效状态变化而移动
—— 详见 §5.4。

### 2.1 `doc_id` 契约

```
doc_id = {机构代码}-{三位流水号}        例：PBC-001、CSRC-024、SPC-007
```

- **不带年份。** 年份信息已在 `publish_date` / `effective_date` 里，重复进 ID 只会让 ID 随
  修订版变动，破坏引用稳定性。
- **机构代码**取 `org` 串里**首个机关**（顿号切分后第一段，见 `_meta.py: first_agency`）。
  机构沿革合并到现行代码：银监会 / 保监会 / 银保监会 / 国家金融监督管理总局 都记 `NFRA`。

| 机构代码 | 机关 | 当前池内份数 |
|---|---|---|
| `PBC` | 中国人民银行 | 75 |
| `CSRC` | 中国证券监督管理委员会 | 24 |
| `GOV` | 国务院 | 16 |
| `NFRA` | 国家金融监督管理总局（含银保监会/银监会/保监会） | 16 |
| `NPC` | 全国人民代表大会及其常务委员会 | 12 |
| `SPC` | 最高人民法院 | 7 |
| `SSE` | 上海证券交易所 | 5 |
| `SZSE` | 深圳证券交易所 | 2 |
| `CAC` | 国家互联网信息办公室 | 1 |
| `BSE` | 北京证券交易所 | 1 |
| | **合计** | **159** |

- **流水号按目录遍历顺序发，发完即冻结。** 一个机构一个池，从 `001` 起递增。
- **冻结的含义：已发放的 `doc_id` 永不重编。** 因此**禁止在 `有效文件/` 内移动、增删文件**——
  遍历序一变，同一份文件可能拿到不同流水号，P1 建好的向量库与 P3 存下的 `clause_id` 会全部失配。
  确有文件要移出时，先冻结当批 ID，再按 §5.4 另立规则。
- 新增文件追加到池尾（下一个可用流水号），不复用已停用编号。

### 2.2 `clause_id` 契约

`clause_id` 是**条级**的溯源键，由 P1 在切分时生成，P3 用它做 /api/v1/clause/{clause_id} 查询。

```
clause_id = {doc_id}-{原文锚点}
```

锚点**照抄原文自己的编号**，不用我们内部的块序号。理由：块序号取决于切分实现，换一次切分
参数就全变；原文编号是作者写的、印在纸上的，稳定，且能直接告诉用户「这是第五十三条」。

| `clause_scheme` | 锚点格式 | 例子 | 说明 |
|---|---|---|---|
| `第X条` | `A` + 条号阿拉伯数字 | 第五十三条 → `A53`<br>第一条 → `A1`<br>第一百零三条 → `A103` | 中文数字一律换算成阿拉伯数字；「零」「〇」记 0，「十」单独出现记 10 |
| `一、二、三` | `S` + 项序号阿拉伯数字 | 三、 → `S3` | 用**出现次序**，不用字面值——顿号项在节内可能重新从「一、」编号，字面值会撞车 |
| `X.Y.Z` | 原编号，**保留点号原样** | 3.6.2 → `3.6.2` | 编号本身已是稳定标识，不加工 |

完整示例：

```
PBC-001-A53        中国人民银行法 第五十三条
PBC-013-S3         关于进一步优化跨境人民币政策…的通知 第三项
SSE-002-3.6.2      上海证券交易所交易规则 3.6.2
```

- 锚点内**不含**分隔符 `-`，故 `clause_id` 用**第一个** `-` 切分即可还原 `doc_id`。
- `clause_scheme = 无` 时不产生 `clause_id`（当前 159 份无此情况）。
- 一个 `doc_id` 下的 `clause_id` 必须唯一。`一、二、三` 用出现次序正是为保证这一点。

## 3. `clause_scheme` 判定规则（有序，先命中者胜）

切分锚点 = 行首出现的、可作为分段边界的编号。判定按全文扫描，**按序试，第一个过门槛的取值胜出**：

| 序 | 取值 | 正则（`re.M`） | 计数方式 | 门槛 | 典型文件 |
|---|---|---|---|---|---|
| 1 | `第X条` | `^\s*第([一二三四五六七八九十百零〇\d]+)条` | 条号**去重**计数 | ≥ 3 次 | 法律、行政法规、部门规章 |
| 2 | `一、二、三` | `^\s*([一二三四五六七八九十]+)、` | **不去重**（节内可能重编号） | ≥ 2 次 | 通知、公告 |
| 3 | `X.Y.Z` | `^\s*(\d+(?:\.\d+)+)(?![\.\d])\s*[\s　]?(?=\S)` | 编号**去重**计数 | ≥ 3 次 | 交易所规则、JR/T 行业标准 |
| 4 | `无` | — | 计 0 | — | 当前 159 份中无此情况 |

当前分布：`第X条` 119 / `一、二、三` 32 / `X.Y.Z` 8 / `无` 0。

> 上表第 4 行是 `clause_scheme` 的兜底值，与 `doc_type` 无关。另注：`doc_type` 的
> **`部门规章`** 此前只写在枚举里、没有文件落在对应子目录下；`NFRA-016` 起落在
> `数据源\4.国家金融监督管理总局\有效文件\部门规章\`，`_meta.doc_type_of` 按子目录名认，
> 判据见 [README.md](README.md) §4 #5。

### 3.1 为什么 `第X条` 必须去重

正文里的**交叉引用**（「依照第五条规定」「对第3.3.13条规定的…」）与条款标题写法相同。
全文匹配会把引用算成条款。实测虚高幅度：

| 文件 | 全文匹配 | 行首去重 | 真值 |
|---|---|---|---|
| 中华人民共和国中国人民银行法 | 56 | **53** | 53 |
| 中华人民共和国信托法 | 79 | **74** | 74 |
| 中华人民共和国商业银行法 | 102 | **95** | 95 |
| 中华人民共和国保险法 | 203 | **185** | 条号 1–185 连续无缺口 |

### 3.2 为什么 `一、二、三` 必须排在 `X.Y.Z` 前面

附件表格里的数字（债券项目目录的品类代码、标准的分级编号）会被 `X.Y.Z` 正则命中。
实例：《绿色债券支持项目目录（2021年版）的通知》正文用顿号分条，附件目录是纯数字表，
若 `X.Y.Z` 先判会得到 275 个假锚点。顿号是作者显式书写的分条标记，优先级必须更高。

### 3.3 为什么 `X.Y.Z` 需要 ≥3 次命中

单次命中多半是年份、金额、页码。交易所规则与行业标准均远超 3 次（实测最低 5 次）。

### 3.4 为什么 `第X条` 需要 ≥3 次命中

没有门槛时，正文里孤零零一处**行首**的「第X条」就能压过几百个 `X.Y.Z` 式条号。
实例：北京证券交易所股票上市规则、深圳证券交易所创业板股票上市规则各有 1 处这样的行首命中
（正文援引「第五条规定」恰好落在行首），154 页的规则整篇被判成 1 个切分单元。

加 `MIN_HEAD = 3` 后这两份正确落到 `X.Y.Z`（379 / 390 个单元）。回归验证：全库仅这 2 行 4 个
单元格变化，无其他影响；《绿色债券支持项目目录》仍正确判为 `一、二、三`（§3.2 的设计未被破坏）。

门槛取 3 而非 2，是为大于「正文偶发一处引用 + 一处真标题」的最坏情况；真正按条写的文件
条数都在 10 以上，3 这个门槛不会误伤。

### 3.5 取文本的方式会影响计数（P1 必读）

**DOCX 必须连表格一起读，但表格单元格必须去重。** 上交所的指引、上市规则把大量条文
放在表格里，只读 `paragraphs` 会漏内容；可 python-docx 对**合并单元格会在每个被合并的
位置重复返回同一段文本**——`SSE-001` 的表头「十一、承诺」横跨 18 行，被读成 18 个连续
锚点、18 条 5 字"条文"。实测该文件 1321 次单元格读取里只有 235 次是真的，**82% 是重复**。

三种读法的实测值（`SSE-001`）：

| 读法 | 锚点数 |
|---|---|
| 只读 `paragraphs` | 162 |
| `paragraphs` + 表格（朴素） | **365** ← 重复读撑出来的 |
| `paragraphs` + 表格（去重） | **173** ← 正确 |

全库影响：只有 `SSE-001` 一份中招，锚点总数 8022 → **7830**。

**PDF 分页拼接必须用 `"\n".join`，不能用 `"".join`。** 后者会把上一页末行与下一页首行粘成一行，
行首锚点被吃掉。

`_meta.py: read_text` 即为基准实现。P1 若用别的库抽文本，切出的单元数应能与本表
`clause_count` 对齐；对不上先查这两条。

### 3.6 行首「第X条」的援引假锚点

PDF 排版会把**援引他法**的条号断到行首：

```
……适用《期货交易管理条例》
第八十二条的规定……
```

这处的「第八十二条」是《期货交易管理条例》的，不是本文的，但它行长在行首、
形状与真条款完全一样，会被 `RE_HEAD` 收进来，把 `clause_count` 抬高 1。

**判据：行首「第X条」之前的文本，若以书名号 `》` 收尾，则该条号属于被援引的法规，剔除。**

```python
REF_TAIL = re.compile(r"》\s*$")
```

实测全库只影响 2 份，且逐一核对确认两处都是援引：

| doc_id | 剔除的假锚点 | 实际援引 |
|---|---|---|
| `CSRC-020` 股票期权交易试点管理办法 | 第八十二条 | 《期货交易管理条例》 |
| `PBC-057` 人行公告〔2026〕第25号 | 第三十一条 | 《征信机构管理办法》 |

**判据为什么取最窄的这一种。** 试过更宽的「前一行不以句末标点收尾即剔除」，
一次命中 118 份里的 111 份，把「第一条」这类真条款也一并杀掉——因为正文首条前面
本来就不是句末标点。宽判据看似更严谨，实则是把整个体例判废。宁可漏（留一个假锚点）
不可错杀（少一个真条款），故只保留 `》` 收尾这一条，宁窄勿宽。

**这两处也被条款号连续性检查独立抓到。** 真条款都是连续的 1..N，假锚点必然在 N 之外
留一个孤点：

| doc_id | 剔除前条号集合 | 剔除后 |
|---|---|---|
| `CSRC-020` | 1..30 连续，**另外多出 82** → 31..81 全缺 | 1..30 连续 |
| `PBC-057` | 1..29 连续，**另外多出 31** → 第 30 条缺 | 1..29 连续 |

连性的判据与 `》` 尾的判据互不相关，却指向同两处，是这条规则可信的主要依据。
按 `第X条` 全库查一遍：剔除前 116 / 118 = 98.3% 无跳号，剔除后 **118 / 118 = 100%**。

## 4. 枚举判定依据

- `doc_type` 由目录位置决定：`1.` → 法律/司法解释，`2.` → 行政法规，`3.` → 部门规章/规范性文件
  （有「令」号者为规章，其余为规范性文件），`4.` → 法律行政法规/行政规范性文件，
  `5.` → 部门规章，`6.` → 自律规则，`7.` → 行业标准。
- `domain` 按**主题**判，不按发文机关判。判之前必须先剥掉发文机关前缀，否则
  「中国银行保险监督管理委员会」里的「保险」会把银行类文件误判成保险。
  前缀可能连着一串（「中国人民银行 中国银行保险监督管理委员会 关于印发…」），
  必须**反复剥到剥不动为止**——只剥一层的话第二个机关名会留下来，同样污染判定。
- `domain` 规则有先后：`外汇 > 证券 > 保险 > 银行`。「保险公司发行**资本债券**」这类会被
  证券规则先命中，若主题实为保险，用 `OVERRIDE` 表人工压正。
- `org` 与 `domain` 相互独立：银行与保险两类制度同出国家金融监督管理总局，
  机构沿革为 银监会+保监会 → 银保监会(2018) → 国家金融监督管理总局(2023)。

## 5. 异常约定

本表为离线产出，无接口错误码。生成阶段的失败约定：

- 单个文件读取失败 → `clause_count = -1`，`note` 追加 `读取失败:<原因>`，**该行仍需输出**，
  不中断整批。`doc_id` 仍按机构分配，取不到机关时用 `UNK` 前缀。当前 159 行无读取失败。
- 正文取不到标题 → 回落到文件名解析结果。
- 公告类确无正式标题（正文与文件名都没有） → `doc_title` 用 `机关 公告〔Y〕第N号`
  这一法定称谓，并在 `note` 标注「公告类无正式标题，以机关+文号代标题」。**禁止编造标题。**
- 文件名被截断（本批有多份，如 `…（银发〔20.pdf`）→ 一律从 PDF 正文恢复真实标题与文号；
  若正文也取不到，**改文件名**而不是编造。改名后必须重跑全表。

### 5.1 `doc_number` 取值规则

**序号式取沿革行的最后一个令号。** 带修订沿革的文件，标题下的括注列出全部沿革：

```
证券交易所管理办法
（1997年11月30日国务院批准 … 2001年12月12日证监会令第4号重新公布
  … 2021年10月30日证监会令第192号第三次修订）
```

印发时的令号在前、现行版的在后，取第一个会把文件标成早已被修订掉的版本。
实测 11 份会中招（储蓄管理条例 107→588、证券交易所管理办法 4→192 等）。
两个坑：「令」后的「第」可有可无（`国务院令666号` / `证监会令第166号` 并存于同一处）；
PDF 换行会切断机关名（`证\n监会令第229号`），故匹配前先压掉全部空白。

**令号的年份有三种写法，都要认，且照抄沿革原文、不重排格式：**

| 写法 | 例 | 谁在用 |
|---|---|---|
| 无年份 | `国务院令第660号`、`证监会令第54号` | 国务院、证监会 |
| `〔〕` | `中国人民银行令〔2005〕第3号` | 人行 |
| `YYYY年` | `国家金融监督管理总局令2023年第4号` | 银保监会 / 总局（`NFRA-016` 起才有） |

第三种是 `NFRA-016` 带进来的。**年份不能丢**——总局与银保监会的令号**逐年重排**，
光看 `令第4号` 会与别的年份撞上。文号是对外引用串，不改成 `〔2023〕` 那种我们喜欢的格式
（与「文号以正文为准」同一条原则）。实现见 `_meta.NO_SEQ` 与 `doc_no_from_body`。

> 文件名里**不要**带这种文号：`_meta.parse_std` 的 `HW` 只认 `〔Y〕`，认不出会把它当成机关名
> 塞进 `org`，`AGENCY_CODE` 随即 `KeyError`。`NFRA-016` 的取名踩过这个坑，
> 最后靠「文件名不带文号 + 正文优先」解决，见 [README.md](README.md) §4 #5。

**年号式文号（`银发`/`金规`/`公告`/`法释`/`银保监发`…）不参与沿革，文件名优先于正文。**
正文里出现的令号可能是它援引的别的法规。实例：《…融资担保公司监督管理条例四项配套制度的
通知》正文援引国务院令第683号，但它自己的文号是 `银保监发〔2018〕1号`。

**文件名里的文号可能不在首个括号组。**《…关于印发《储蓄国债（凭证式）管理办法》的通知
（银发〔2021〕20号）》的首个括号是「（凭证式）」，逐一检查每个括号组、取装着文号的那一个。

**取不到就留空，不编造。** 当前 22 份为空，全部有据：

| 类别 | 份数 | 依据 |
|---|---|---|
| 法律 | 12 | 体例上无文号，以主席令公布 |
| 交易所自律规则 | 8 | 交易所非行政机关，无发文字号 |
| `证券、期货投资咨询管理暂行办法` | 1 | 1997 年国务院批准、国务院证券委员会发布，无国务院令号 |
| `关于促进债券市场信用评级行业健康发展的通知` | 1 | 五部门联合发布，官网未标发文字号 |

### 5.3 日期列与留空列

- `publish_date` / `effective_date` / `fetched_at` 都是**整数** `YYYYMMDD`，不是字符串，也不是日期格
  —— 便于 Milvus 做范围过滤。
- `publish_date` 依次尝试三条路，先命中者胜。当前 **148 / 159** 有值。
  1. **头部区间最后一个中文日期**（`head_region`，上限 4000 字）。令头文件的最后一个日期是公布日，
     带沿革行的文件是现行版那一次修订的日期。取不到则退回月精度（交易所规则的沿革只印到
     「2026年4月第二十次修订」），记该月 1 号，`note` 标注「publish_date 精度到月(原件只印年月)」。
     **但沿革行同时印公布日与施行日时，最后一个日期是施行日**（写法形如
     `(2023年10月26日国家金融监督管理总局令2023年第4号公布 自2024年1月1日起施行)`）——
     取之前要先剔掉被当施行日在用的那个日期，判据见 `_meta._is_effective_at`。
     漏了这条会成批填错，本库实测中招 8 份（`CSRC-002/011/012/013/014`、`PBC-036/037`、`SPC-001`），
     2026-10-27 已改正，留痕见 `脚本/_pubdate_fix.py`。
  2. **行业标准封面**：`2020 - 02 - 13 发布`。这是全库唯一一处阿拉伯数字日期，别写成紧贴的
     `\d{4}-\d{2}-\d{2}`——**连字符两侧有空格**（PBC-074 / PBC-075）。
  3. **文末落款日期**（`tail_sign_date`）：通知类正文开头是主送机关、没有日期，发布日期只在
     文末机关署名之后。如 PBC-053 / PBC-059 / PBC-068 / PBC-058 一批。
     **落款日期必须与「引用」区分开**，两个排除条件缺一不可：
     - 前置「自」→ `自2022年1月1日起施行` 是**施行日**不是发布日（GOV-008 会中招）
     - 后接「发布/公布/印发」→ `2021年3月18日发布的《…》同时废止` 是**它废止掉的旧版**
       的日期（CSRC-001 会取到 20210318、CAC-001 会取到 20200413，都错）

     这两条是本轮实测踩出来的：不加排除条件，文末落款取法会给 3 份填上错值。
     **宁可留空，不可填错**——错值比空值危害大，P3 会把用户引到别的文件上。
- `effective_date` 取全文**最后一个**「自 YYYY年M月D日 起 施行/实施/生效/执行」；若全文写
  「自发布/印发/公布之日起施行」则等于 `publish_date`。两处放宽都来自实测：
  - 动词不止「施行/实施/生效」：PBC-033 写的是「自2024年2月18日起**执行**」
  - 「起」可有可无：PBC-070 写「本办法自2023年1月9日施行」
  - 「自」可有可无：CSRC-008 写「本办法公布之日起施行」
  - 行业标准封面 `2020 - 02 - 13 实施`（同 `publish_date` 第 2 条）

  当前 **150 / 159** 有值。
- `fetched_at` 取文件落盘时间（`os.path.getmtime`）。这是近似值，但本机采集后即就地留存，
  没有更可靠的记录。当前 159 / 159 有值。
- **`expire_date` 当前全表为空，这是有意为之，不是遗漏。** 本库不含废止日字段，
  废止信息只在「废止件」的正文里（本库 1 份）。取不到就留空——**宁可空，不可编。**
- **`source_url` 有三类来源**：一批是**文件正文/页脚自己印的**官方 URL（真抽取，20 份）；
  其余靠**联网查证官方页**回填，做法、校验与踩到的坑见 §8.3；
  `NFRA-016` 是**本次采集时直接记下的来源页**（第 3 类，只此 1 份）。
  **三类都必须版本一致才填**——
  指向旧版文件的 URL 比留空更坏，`note` 里逐行留了来源。查不到的留空，
  **不得由标题反推伪造**。
- **`topic_tags` 已回标 159 / 159**（第 6 步）。22 个业务条线标签，每份 1~3 个，
  词表、定义与逐份回标留痕见 `产出/topic_tags_词表.md`。归属记在
  [README.md](README.md) §4 —— 原先本节写的「应由 P1 检索侧或 P3 生成」已作废。

### 5.4 `status` 枚举与文件位置

`status` 由时效核查得出，三值：`有效` / `尚未生效` / `已废止`。当前
`有效` 155 · `尚未生效` 3 · `已废止` 1。

**第四个值 `已修订` 是保留值，当前 159 行没有。** 技术方案 §11 的增量更新场景要求「文档被修订时
旧版置 `status=已修订`、新版按新 `doc_id` 入库，两者都留以便溯源」；而 §1 只收 `有效文件/` 目录，
`旧版(已被修订)` 整目录不收。两条规则目前并存未裁决（README §4 待裁决 #1）。

**对 P1/P3 的影响**：过滤代码里 `status` 的合法取值**按四值写**（`有效`/`尚未生效`/`已废止`/`已修订`），
不要假设只有三种。若第 11 周裁决为「启用增量更新」，旧版条文会以 `已修订` 进库；届时
`/api/v1/meta/filters` 的 `status` 枚举会多一项，前端筛选器不需改动。

- `尚未生效`：附则写明施行日晚于采集日。当前 3 份 —— 金规〔2026〕8号（2027-03-01 起施行）、
  金规〔2026〕9号（2026-11-01 起施行）、人行公告〔2026〕第25号（2026-11-15 起施行）。
  P1 检索时可用 `effective_date > today` 过滤，避免用未生效条文回答。
- `已废止`：当前 1 份 —— 银发〔2021〕237号《关于进一步防范和处置虚拟货币交易炒作风险的通知》，
  已被同库 银发〔2026〕42号（`PBC-015`）取代。

**为什么废止件还留在 `有效文件/`：** `doc_id` 一旦发放即冻结（§2.1），而流水号按目录遍历顺序
发放。把文件移出 `有效文件/` 会改变遍历序，导致同目录其余文件的 `doc_id` 全部错位，
P1 已建好的向量库与 P3 存下的 `clause_id` 会集体失配。因此**状态用列表达，不用文件位置表达**。
入库时按 `status` 字段过滤，不要按目录过滤。

技术方案表里没有。**换出 0 份的，补进有份的，合计仍是 159。**

**本表未采用技术方案表8 的三个字段，理由记录在此：**
- `embed_text`、`is_short`：切分与向量化是 P1 的工序，P2 在文档级无从产生。
- `chapter`、`clause_no`、`clause_index`：条款级字段，属 P1 切分产物，见 §2.2 的锚点契约。
- `text`：正文，P1 直接从源文件取（§3.5 的取文本规则同样适用），不必经本表中转。

**另：技术方案 表8 标注 `source_url` / `effective_date` 为必填，本表达不到，
处理办法见 §8。**

## 8. 硬指标的裁决

技术方案 表8 把 `source_url` / `effective_date` 标为必填，表13 又要求「必填字段 100% 非空」。
本表两条都达不到。硬凑到 100% 只有三条路，逐条看是否成立。

### 8.1 现状

| 列 | 技术方案要求 | 本表实际 | 覆盖率 |
|---|---|---|---|
| `publish_date` | 必填 | 148 / 159 | 93.1% |
| `effective_date` | 必填 | 150 / 159 | 94.3% |
| `source_url` | 必填 | 141 / 159 | 88.7% |
| `topic_tags` | 选填 | 159 / 159 | 100% |
| `expire_date` | 选填 | 0 / 159 | — |

（`publish_date` / `effective_date` 本轮各补回 9 / 6 份，见 §5.3。补回前是 138 / 138。
2026-10-27 加 `NFRA-016` 一份（四项日期列都有值），分母 158 → 159，故 `publish_date` 147→148、
`effective_date` 149→150、`source_url` 140→141。**日期修正在同一轮里有反向的**：
`CSRC-002` 等 8 份是**改错值不改非空数**，所以覆盖率没变，别拿覆盖率当「日期对不对」的指标。）

### 8.2 `effective_date`：保留必填，用「法定默认」补，不编造

**为什么这条不能丢。** 时效性是本项目的**核心差异点**（立项书里的「避免用已废止条文回答」）。
P1 的过滤条件就是 `effective_date <= today`。该列一旦为 NULL，Milvus 的范围过滤会静默漏掉这份
文件——不是报错，是查询结果里**少几条**，最难发现的那种错。所以这条必须尽量填满，
且**填的值必须是真的**。

**能不能补。** 剩下 14 份空值里，13 份 `status = 有效`。逐份看原因，**没有一份是解析漏掉的**，
都是原文确实没写施行日：

| 原因 | 份数 | doc_id | 说明 |
|---|---|---|---|
| 修正版司法解释 | 2 | `SPC-003` `SPC-006` | 施行日写在**修正决定**里，不在被修正的正文里 |
| 通知类正文无施行句 | 5 | `PBC-069` `NFRA-010` `NFRA-011` `NFRA-012` `NFRA-013` | 通篇不出现「施行」二字 |
| 拟废止件 | 1 | `PBC-011` | 已废止，本就无需施行日 |
| 附件而非独立制度 | 2 | `PBC-012` `SSE-003` | 一个是目录附件，一个是上市规则的「暂缓实施条文」附表 |
| 「自公布/印发之日起施行」但发布日也缺 | 3 | `CSRC-009` `NFRA-014` `PBC-067` | 需先有 `publish_date` 才能推。`PBC-067` 是「自发布之日起**六个月后**施行」，相对日期，更不该猜 |
| 附件表单 | 1 | `PBC-020` | 境外机构签章样表 |

合计 2 + 5 + 1 + 2 + 3 + 1 = **14**，与 `effective_date` 空值数一致。

**建议的补法（待裁决）：** 对「通知类无施行句」这 5 份（`PBC-069` / `NFRA-010` / `NFRA-011` /
`NFRA-012` / `NFRA-013`），按**法定默认**回填：部门规范性文件未另定施行日的，自发布之日起施行。
这**不是编造**——它是这类文件的法定生效规则，回填的值就是真实生效日，且这 5 份都有 `publish_date`。
回填后 `effective_date` 达 **150 / 159 = 94.3%**（回填那 5 份不变，`NFRA-016` 另有值），
每一条都留 `note` 说明是按默认规则推的。

**不建议补的：** `SPC-003` / `SPC-006` 的施行日在修正决定里，属本库之外的事实，
要填就得外部查证（可查，但需另行确认）；`PBC-012` / `SSE-003` / `PBC-020` 建议**考虑剔除**
（见 §8.4）；`CSRC-009` / `NFRA-014` / `PBC-067` 因 `publish_date` 也缺，无从推。

### 8.3 `source_url`：必填仍建议丢掉，但实测能补回大半

**为什么必填仍该丢。** 本项目的「溯源」需求是**定位到哪份文件、哪一条**——这个由
`doc_title` + `doc_number` + `clause_id` 已经完整满足（§2.2）。URL 是「方便点开原文」，
是增强不是必需。而 158 份的原始下载 URL **当初没随文件留存**（`NFRA-016` 是唯一例外——
它从采集那一刻起就有来源页），靠标题反查有风险，
**查错等于把用户引到别的文件上**，比留空危害大（风险的具体形状见下面那条规则）。

**「正文页脚」那条路，回来逐份核了一遍，基本是死的。** 本节原先实测「25 份正文里印着
官方 URL」，剔除多 URL 的之后估 20 份可确定性回填。真要落表时逐份读，这批 URL 大半是
**打印网页时带下来的站点导航页脚**（首页、栏目页、子站入口），不是该文件的详情页。
指向栏目页等于丢给用户一个「你自己找」的入口，不算溯源。那 20 份的来源已在 `note` 里
标成「正文页脚」，**保留不动**（它们确实是文件自身印的），但**不再当主力路径**。

**主力改成联网查证，成效比原先预估的好。** 上节判为「不建议」的选项 C 实际做了，
理由是：`doc_title` + `doc_number` 在官方站上**可以唯一命中**，不是猜。做法是六个并行子代理
分头查、结果落 `产出/_url_results_*.json`，再由 `脚本/_merge_urls.py` 校验后合并 ——
校验包括 doc_id 在清单内、无跨文件重复、**域名在白名单内**、`confidence` 与 URL 空/非空自洽、
URL 不超 512 字节。**代理的返回值一律不当结论，只当线索。**

（六份结果覆盖 158 份里缺 URL 的**全部 138 份**，最终落表 **120 份**，另有 20 份原本就由正文页脚提供，
合计 **140 / 158 = 88.6%**。未落表的 18 份 = 11 份查不到 + 7 份查到旧版主动不填。
加上 `NFRA-016` 后是 **141 / 159 = 88.7%**，空值数仍是 18 —— **分母变大而空值不变**，
别看到「还是 18」就以为没动过。）

**但查证查出一条必须写下来的规则：官方页存在 ≠ 可填。**

这是本轮的同一个坑**踩到第三次**：

| 次 | 现象 | 判据 |
|---|---|---|
| 1 | `gov.cn` 上的「孪生件」正文与入库件差 3%~15% | 逐字比对 |
| 2 | `SPC-006` / `SPC-007`：代理标 `verified`，但 `court.gov.cn` 页是 2013 / 2018 **首发版**；本库正文含「2020年12月23日最高人民法院审判委员会第1823次会议通过」，是 **2020 修正版** | 读入库正文的修正沿革 |
| 3 | `CSRC-003` / `004` / `017` / `024`：代理标 `title-only`，官方规章页沿革停在 2020 年令第166号等；本库是 **2025-02-19 第227号令**修订后版本 | 读入库正文的施行条款 |
| 4 | `GOV-010`：**另一种形态 —— 不是「页是旧版」，是「根本没有」**。白名单域名上只有 2006-11-11 令第478号原版；本库是 2019-09-30 第三次修订版 | 同上 |

注意第 2、3 次的**置信标签是反的**：标 `verified` 的两份该拒，标 `title-only` 的四份也该拒。
所以判据不能是代理的标签，只能是**拿起入库件自己的正文，去比官方页的版本**。
**「找到个不对的」和「压根没找到」结论一样是留空** —— 第 4 次就是后者。
这 7 份的 URL 一律丢弃，`note` 写明「官方页版本与入库件不一致」
（裁决理由逐条记在 `脚本/_merge_urls.py` 的 `HOLD` 常量里）。

**反过来，标 `title-only` 的不必一律拒：** NPC 那 12 部法律全标 `title-only`，
只因为**本表 `doc_number` 为空**（法律不带令号），代理无法核对文号而自降置信度；
版本上它们与入库件逐字一致（比对的是入库正文头印的修正沿革，如 `NPC-010` 的
「2019年12月28日……第二次修订」对 flk 页的公布日期 2019-12-28），全部接收。
**标签只是线索，判决始终靠正文。**

**结论：填 URL 的前提是版本一致，不是页面存在。** 指向旧版的 URL 比留空更坏 ——
用户照着去核，核出来的是别的条文，会直接动摇对系统的信任。

**三个选项（原样保留，供追溯）：**
- **A**：丢掉 `source_url` 的必填，把能确定的填上，`note` 标注来源。
- **B**：158 份全留空，`source_url` 从必填降为选填。
- **C**：逐一联网查证补齐。**实际采用了 A + C 的混合**：必填丢掉（A），同时联网查证（C），
  查不到的留空。C 原先的否掉理由是「查到的 URL 无法用本库自证」，这条**已被推翻** ——
  可以自证，用入库正文的修正沿革/施行条款反查官方页版本即可，见上表。

### 8.4 建议丢弃的必填项与建议剔除的件

**`expire_date` / `topic_tags`：本就可以空。** 技术方案 表8 这两列本就标选填，
`expire_date` 的信息在「废止件」的正文里（本库 1 份）。**无需处理。**

> **`topic_tags` 的归属，本节原先写的是「应由 P1 检索侧或 P3 生成，P2 不预先猜」，与
> [README.md](README.md) §4 待裁决 #3「P2，第 5 周」冲突。以 README 那份决议台账为准：P2 主责。**
> 理由：`/api/v1/meta/filters` 与前端筛选器读的是这张元数据表，标签必须落在表里才可用；
> 且标签是从**标题与条文内容**归纳出来的（归并规则可复核），不是凭空猜的，不违背本节「宁可空不可编」的原则。
> 归并出的词表与逐份回标结果写进 `产出/` 并留痕，便于复核。

**建议剔除的 3 份（待裁决，剔除会改变行数 159 → 156，`doc_id` 需重排，见下方风险）：**
- `PBC-012`《绿色债券支持项目目录（2021年版）》——**已被同库 `PBC-029` 的 2025 年版替代**，
  且本库收的是**附件目录**不是通知，无发布/施行日。
- `SSE-003`《上海证券交易所交易规则（2026年修订）暂缓实施条文》——是上市规则的**附件**，
  内容是「哪些条暂缓实施」的列表，不是独立制度，且「暂缓」状态本身会变。
- `PBC-020`《境外机构境内发行债券资金管理有关事宜的通知》——本库收的是**签章样表附件**，
  正文 2 条，无日期。

**剔除的代价（必须知道）：** `doc_id` 按目录遍历序发放（§2.1），抽掉 3 份会让同目录其余文件的
`doc_id` 全部前移，P1 已建的向量库、P3 已存的 `clause_id` **集体失配**。所以：
- 若 P1/P3 **尚未开始**建库 → 现在剔，代价为零。
- 若**已经开始** → **不剔**，改为在 `note` 标注「建议剔除：<原因>」，由 P1 入库时按 `note` 过滤。

### 8.5 结论

| 项 | 建议 | 覆盖率达到 |
|---|---|---|
| `effective_date` 必填 | **保留**，5 份按法定默认回填 | 150 / 159 = 94.3% |
| `source_url` 必填 | **丢掉**；正文页脚 20 份 + 联网查证 120 份 + 采集即留 1 份 | **141 / 159 = 88.7%**（其余 18 份留空：11 份白名单域名内查不到，7 份查到的是**旧版本**、与入库件不一致故意不填） |
| `expire_date` / `topic_tags` | 不动（本就选填） | — |
| 表13「必填 100% 非空」 | **改为「≥ 90%」**，并在技术方案里写明哪几类允许空 | — |

**表13 那条指标本身要改。** 「必填字段 100% 非空」对**离线汇总的语料元数据**是不成立的指标：
总有文件的原文不印日期。硬凑到 100% 只能靠编。**指标该改，不是数据该凑。**

> **⚠️ `source_url` 另有合规问题，与覆盖率无关。** 140 条里有 **74 条（52.9%）落在
> `robots.txt` 为 `Disallow: /` 的域名上**（`pbc.gov.cn` 系 66 条、`flk.npc.gov.cn` 8 条——后者
> robots 首行明文「禁止使用任何自动化工具、脚本、爬虫程序采集或复制网站数据」）。
