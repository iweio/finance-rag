# 从数据源到前端：一条流水线走一遍

一句话：**把散落在政府官网的 159 份制度文件，变成 Milvus 里 8156 条带完整元数据的条文向量，让用户问「商业银行贷款应当遵守哪些资产负债比例管理规定」时，系统答得出来、并且指得出这句话出自哪部法规的第几条。**

> 示例问题不能随手挑。原先这里举的是「核心一级资本充足率不得低于多少」，而**《商业银行资本管理办法》不在当前语料里**（见文末「语料有个已知缺口」），拿它当例子会以为系统该答得出、实际答不出。

下面从数据源开始，一步一走到前端。每一步都写清四件事：**进来什么 → 做什么 → 出去什么 → 怎么验**。

```
①数据源      ②解析      ③清洗      ④切分      ⑤元数据     ⑥标签
159 份   →  纯文本   →  干净文本  →  8156 条  →  159×19  →  domain/tags
                                         ↓
⑫前端  ←  ⑪API  ←  ⑩生成  ←  ⑨检索  ←  ⑧入库  ←  ⑦向量化
 Vue3     8 接口    LLM      混合检索   Milvus    bge-m3
```

## 第 1 步：数据源 → 编号

**进来什么**：159 份文件、6 个目录。
**做什么**：给每份文件发一个**永久身份证 `doc_id`**。
**出去什么**：`PBC-001` … `PBC-075`、`CSRC-001` … `CSRC-024`、`GOV-001` … `GOV-016`、`NFRA-001` … `NFRA-015`、`NPC-001` … `NPC-012`、`SPC-001` … `SPC-007`、`SSE-001` … `SSE-005`、`SZSE-001` … `SZSE-002`、`CAC-001`、`BSE-001`。

```
doc_id = {机构代码}-{三位流水号}      例：PBC-001
```

机构代码：`PBC` 人行 / `NFRA` 金融监管总局 / `CSRC` 证监会 / `GOV` 国务院 / `NPC` 全国人大 / `SPC` 最高法 / `SSE` 上交所 / `SZSE` 深交所 / `BSE` 北交所 / `CAC` 网信办。

**编号里没有年份**，这是刻意的。技术方案写的是 `PBC-2023-001`，但年份已经存在 `publish_date` 列里，再存一遍只会让同一机构跨年重号。

### 这一步的两个硬规矩

**① 号池一旦发出即冻结。** 流水号按目录遍历顺序发放，不是按文件名排序。**把任何一个文件移出目录，都会让它后面所有文件的流水号错位**——P1 已经建好的向量库和 P3 存下的 `clause_id` 会集体失配。

这就是为什么那份唯一"已废止"的文件还留在 `有效文件/` 目录里（第 5 步详说）。

**② `doc_id` 是所有下游键的根。** `clause_id = doc_id + 原文锚点`，Milvus 主键是 `clause_id`，API 路径参数是 `clause_id`，前端溯源的锚是 `clause_id`。根变了，整条链全断。

**验什么**：`doc_id` 全局唯一、格式合规、10 个号池份数与预期一致 → `_verify.py` 第 4、5 项。

## 第 2 步：解析 → 纯文本

**进来什么**：159 份 PDF/Word。
**做什么**：把每种格式读成纯文本。
**出去什么**：`产出/clean/{doc_id}.txt`。

### 先判断走哪条路

```python
doc = fitz.open(path)
avg = len(text.strip()) / max(doc.page_count, 1)
route = "ocr" if avg < 50 else "hybrid" if avg < 200 else "text"
```

| 路线 | 判定 | 工具 |
|---|---|---|
| `text` | 平均每页 ≥ 200 字符 | PyMuPDF (`fitz`) |
| `hybrid` | 50~200 | OCR 后与文本层比对 |
| `ocr` | < 50 | PaddleOCR（备选 Tesseract + chi_sim） |

**不做这一步的后果最严重**：对扫描件直接 `get_text()` 会得到空字符串或乱码，**而程序不会报错**。你会以为解析成功，一直到最后发现知识库是空的。这是本项目最大的隐性风险——所以 Milvus 的条数必须暴露在 `/api/v1/health` 里，随时可见。

### 两个实测踩到的细节

**DOCX 要连表格一起读，但表格单元格必须去重。** 上交所的指引把大量条文放在表格里，只读 `paragraphs` 会漏内容；可 python-docx 对**合并单元格会在每个被合并的位置重复返回同一段文本**——`SSE-001` 的表头「十一、承诺」横跨 18 行，被读成 18 个连续锚点、18 条 5 字"条文"。

`SSE-001` 三种读法的实测值：

| 读法 | 锚点数 |
|---|---|
| 只读 `paragraphs` | 162 |
| `paragraphs` + 表格（朴素） | **365** ← 重复读撑出来的 |
| `paragraphs` + 表格（去重） | **173** ← 正确 |

判断依据：该文件 1321 次单元格读取里只有 235 次是真的，**82% 是重复**。全库只此一份中招，锚点总数 8022 → **7830**（这是**当时 158 份语料下**的数；加了 `NFRA-016` 之后当前全库是 **8036**）。见 `脚本/_kb.py` 的 `read_pages()`。

```python
parts = [p.text for p in doc.paragraphs]
for tb in doc.tables:
    for row in tb.rows:
        parts.extend(c.text for c in row.cells)     # ← 这一行不能省
```

**PDF 分页必须用 `"\n".join`。** 用 `""` 会把跨页两行粘成一行，**吃掉行首的锚点**——上一页末尾「……依照本法」，下一页开头「第五十三条」，粘起来变成「……依照本法第五十三条」，这一条的锚点就丢了。

### 扫描件的预处理顺序不能乱

```
原图 → 300dpi → 灰度化 → 自适应二值化 → 去噪 → 倾斜校正 → 表格线检测 → OCR
```

金融文档特有的三个麻烦：**印章遮挡文字、表格线干扰字符切分、双栏排版导致串行**。双栏要按版面坐标聚类——同栏文本块按 y 排序，先读完左栏再读右栏。直接按 y 排序会把左右两栏交错拼在一起，产生语义完全错乱的句子。

命题推荐 Tesseract，但它对中文金融文档（表格线、印章、密排小字）识别率偏低。方案写为「以 Tesseract 为基础，实测后引入 PaddleOCR 提升中文识别率」——这本身就是命题要求的「至少 1 处技术创新」的可答辩点。

**验什么**：每一份都能读出非空文本；抽样比对音频字符准确率 ≥ 90%。

## 第 3 步：清洗 → 干净文本

**进来什么**：原始纯文本。
**做什么**：9 条规则，**按顺序执行，顺序会影响结果**。
**出去什么**：`产出/clean/{doc_id}.txt`。

| 序 | 规则 | 做法 |
|---|---|---|
| 1 | 去页眉页脚 | 统计各页重复出现的行（出现率 > 60%）并剔除 |
| 2 | 去页码 | `^\s*[-—]?\s*\d+\s*[-—]?\s*$` |
| 3 | **PDF 硬换行合并** | 行尾无标点且下行非条款起始 → 合并 |
| 4 | 全角转半角 | 数字、字母、括号、百分号；中文标点保留 |
| 5 | 条款号归一 | `第 十 条` → `第十条` |
| 6 | 去零宽字符 | `​` `﻿` 等 |
| 7 | 压缩空白 | 连续空白/空行压成一个 |
| 8 | 繁简统一 | 官网偶有繁体文本 |
| 9 | **去公文属性块** | gov.cn 的 `索 引 号：主题分类：…` 元数据表被当正文读出来，按行删连续 ≥3 行的属性段 |

**第 3 条最容易出问题。** PDF 每行末尾都硬换行，不合并的话一条完整条文会被拆成十几个短句，embedding 出来的语义是碎的。判断依据：**行尾不是句号/分号/冒号，且下一行不以「第X条」「（一）」开头 → 合并**。

第 5 条是给第 4 步铺路的：PDF 里「第 十 条」中间夹了空格，不归一的话锚点正则匹配不到。

**第 9 条不能「从标记一刀切到文末」。** gov.cn 网页把公文元数据渲染成一张表，另存成 PDF 后这张表被当正文读出来，标签单元格还按表格行数重复（`成文日期：` 连出 7 行才跟一个真值）。中招 6 份：GOV-001/002/004/005/009、NFRA-001，每份最后一条条文的尾巴上粘 360~450 字垃圾。

但这块**不一定在文末**——GOV-001 的属性块夹在正文中间，后面还接着第二十二、二十三条；NFRA-001 后面接着第三十五~三十七条。切到文末会把真条文一起删掉。所以按行取「连续 ≥3 行的属性段」，只删这一段；NFRA-001 的块还与公文标题挤在同一行（`关于印发《…》四项配套制度的通知发文机关：`），因此每行只删从该行第一个标签起的那一截，行首的标题原地留下。

实测：6 份各删 1 段，残留标签 0，块两侧真条文全在，**chunk 总数仍是 8156**（没触发二次切）。

## 第 4 步：切分 → 8156 条

**这一步是整个方案最关键的地方。**

**进来什么**：干净文本。
**做什么**：**按「条」切，不按字数切。**
**出去什么**：`产出/chunks/{doc_id}.jsonl`，一行一个条文；全库合计 **8156 条**。

### 为什么必须按条切

1. 条文是法规的**最小语义单元**，天然边界，比任何启发式切分都准；
2. 命题要求「答案溯源标注对应制度条文」——**必须精确到条**，按字数切就无法标注；
3. 金融问答的问题往往直接对应某一条（「资本充足率要求是多少」→ 直接命中第五十三条）。

按 400 字切，条文被拦腰切断，第 11 步的溯源卡片就没法指向「第几条」了。

### 三种锚点体例

不是所有文件都用「第X条」。实测三种：

| `clause_scheme` | 锚点样式 | 份数 | 实例 |
|---|---|---|---|
| `第X条` | `第一条` … `第五十三条` | 118 | `NPC-001` 中国人民银行法，53 条 |
| `一、二、三` | `一、` `二、` `三、` | 32 | `PBC-002` 人行公告〔2025〕第21号，12 条 |
| `X.Y.Z` | `3.6.2` | 8 | `SSE-002` 上海证券交易所交易规则，**177 条** |

`PBC-075`《金融数据安全 数据安全分级指南》是国标体例，走 `X.Y.Z`，31 条。

按优先级**先命中先赢**，最低命中门槛 `MIN_HEAD = 3`——少于 3 条就不认这个体例，避免把正文里偶然出现的「第三条」当成整个文件的切分依据。

### `clause_id` 的生成

```
clause_id = {doc_id}-{原文锚点}
```

| 原文 | `clause_id` |
|---|---|
| 第五十三条 | `PBC-001-A53` |
| 三、 | `PBC-002-S3` |
| 3.6.2 | `PBC-075-3.6.2` |

**用原文锚点而不是序号**，因为原文锚点在有些文件里**不连续**：`CSRC-020` 只有 1..30 和 82（缺 31..81），用序号会错位。

### 一个实测踩到的坑：援引假锚点

PDF 跨行断句会制造假锚点：

```
……依照《中华人民共和国公司法》
第五十三条的规定，……
```

这里的「第五十三条」是**援引别人的条**，不是本文的一条。它会凭空多算一条。

判据：锚点前一行以 `》` 结尾 → 是援引，跳过。实测修正了 `CSRC-020` 和 `PBC-057` 两份，**`第X条` 文件的条款号连续性从 116/118（98.3%）提到 118/118（100%）**。

### 三种边界情况

| 情况 | 判定 | 处理 |
|---|---|---|
| 超长条 | > 1000 字 | 按「款/项」二次切，加后缀 `第X条-1`/`第X条-2`，片间重叠 50~100 字 |
| 超短条 | < 30 字 | 独立保留，打 `is_short=true`，检索时降权 |
| 无条款结构 | 整篇无「第X条」 | 兜底：按自然段聚合，400 字一片、重叠 100 字，标记 `no_structure` |

**兜底不能省**：规范性文件里有相当比例没有条款编号，直接丢弃会白白损失 20%~30% 的数据量。`clause_scheme` 里目前**没有「无」这一类**，说明 159 份都至少能落进三种体例之一。

### 上下文头增强

```python
embed_text = "《商业银行资本管理办法》第三章 资本充足率 第五十三条\n" + text
```

单看「不得低于百分之五」，模型不知道这是哪部法规的哪一条；加上制度名与条款号后语义锚点明确，检索准确率明显提升。

**`text` 与 `embed_text` 必须分开存两个字段。** 只存 `text` 的话，想补上下文头时就得全库重建。

### 怎么验

- **条款号连续性**（逐篇）：跳号说明解析漏条 → **118/118 连续，100%**
- **长度分布**：中位数应在 100~500 字
- **抽样人工比对**：随机抽 20 条与原 PDF 逐字比对

**验什么**：`clause_id` 无撞车、无空、数量与 `clause_count` 一致 → `_verify.py` 第 15 项。当前 **8036 锚点 / 撞车 0 / 空 0 / 与 clause_count 不符 0**。

再验一遍 `pipeline.py` 自己的两道闸门（跑 `--all` 时自动执行，不过就中止）：

1. **清洗后重测的体例/条数 == `语料元数据.xlsx` 登记的**。清洗会改文本，一旦某条规则吃掉了行首锚点，闸门立刻炸。
2. **切出条文的锚点数 == 锚点数**。超长条二次切只加 `-N` 后缀，不改变这个数。

这两道闸门是被真事逼出来的：清洗的硬换行合并规则曾经要求「`1.1` 后面跟空白」，可真实 PDF 里 `1.1` 是**独占一行**的（`第一章总则⏎1.1⏎为规范证券…`），匹配不上就被并进上一行，锚点当场消失——`SZSE-001` 少了 25 条、`PBC-074` 少了 16 条。

## 第 5 步：元数据 → 159×19

**进来什么**：159 份文件 + 它们的切分结果。
**做什么**：给每份文件填 19 个字段。
**出去什么**：`产出/语料元数据.xlsx`，**159 行 × 19 列**。

完整列定义见 [契约/SPEC.md](../契约/SPEC.md) §2。当前填充情况：

| 列 | 填充 |
|---|---|
| `doc_id` `file_name` `doc_title` `org` `doc_type` `domain` `status` `clause_count` `clause_scheme` `fetched_at` | 159/159 |
| `publish_date` | 148/159 |
| `effective_date` | 150/159 |
| `doc_number` | 137/159（22 份体例上无文号） |
| `source_url` | 141/159（20 份文件正文/页脚自带 + 120 份联网查证 + 1 份采集即记录；查到旧版的 7 份宁可留空，另有 11 份官方站确实没找到）。**⚠️ 其中 74 条落在 `robots.txt` 禁止抓取的域名上，见 [数据来源合规说明.md](数据来源合规说明.md)** |
| `topic_tags` | 159/159（第 6 步回标，见下） |
| `expire_date` | 0/159（本库没有废止日字段） |

### 空值都是有据的，不编造

`doc_number` 那 22 份空值落在四类，全部有出处：

| 类别 | 份数 | 依据 |
|---|---|---|
| 法律 | 12 | 体例上无文号，以主席令公布 |
| 交易所自律规则 | 8 | 交易所非行政机关，无发文字号 |
| `证券、期货投资咨询管理暂行办法` | 1 | 1997 年国务院批准、国务院证券委员会发布，无国务院令号 |
| `关于促进债券市场信用评级行业健康发展的通知` | 1 | 五部门联合发布，官网未标发文字号 |

### 日期为什么存 int

`20240101` 而不是 `"2024-01-01"`。Milvus 对标量日期的范围比较支持有限，存整数后过滤表达式可以直接写：

```python
effective_date <= 20241019
```

存字符串会让时效性过滤写不出来。

### 效力状态：三值

官网不会逐条告诉你这条是否失效。三级判定：

| 级别 | 依据 | 可靠性 |
|---|---|---|
| 文档级 | 官网栏目分「现行有效 / 失效」；或文末载明废止说明 | 高 |
| 规则级 | 新制度明文废止旧制度；文本含「自X日起施行」且 X 晚于今天；`expire_date` 已过 | 中 |
| 默认 | 官网未标注且无废止线索 → `有效` | 低，需抽查 |

当前：**有效 155 / 尚未生效 3 / 已废止 1**。

- `尚未生效` 3 份：金规〔2026〕8号（2027-03-01 起施行）、金规〔2026〕9号（2026-11-01）、人行公告〔2026〕第25号（2026-11-15）。检索时用 `effective_date > today` 过滤，避免用未生效条文回答。
- `已废止` 1 份：银发〔2021〕237号，已被同库 `PBC-015`（银发〔2026〕42号）取代。

**强烈建议人工核对，不要全自动推断。** 自动推断一旦错了，系统会一本正经地引用已废止的条文——这在答辩时是致命伤。

**验什么**：行数 159、列数 19、`status` 分布、日期列全为 int、`source_dir` 路径可打开 → `_verify.py` 第 1、2、9、11、12、13、14 项。

## 第 6 步：标签 → domain + topic_tags

**进来什么**：上面的元数据表。
**做什么**：补两级分类。
**出去什么**：`domain` 列（已有值）+ `topic_tags` 列（**159/159 已回标**）。

### 一级 `domain`（单选，5 个）

## 第 7 步：向量化 → 8156 个向量

**进来什么**：8156 条条文（`text` + `embed_text`）。
**做什么**：用 bge-m3 编码。
**出去什么**：`产出/embeddings/parts/part-000.npy` … `part-007.npy`，每个分片配一份同名 `.jsonl` 记 `clause_id` 顺序，外加 `manifest.json`。

### 模型

**`BAAI/bge-m3`，1024 维。** 理由：条文可能较长（超长条切分后仍可到 800 字），m3 支持 8192 长文本且中文金融语料表现好。

备选：`bge-large-zh-v1.5`（1024）、`text2vec-large-chinese`（1024）、`m3e-base`（768）。

### 三个致命细节

**① query 必须加指令前缀，passage 不加。**

```python
QUERY_PREFIX = "为这个句子生成表示以用于检索相关文章："

query_vec   = model.encode(QUERY_PREFIX + question, normalize_embeddings=True)
passage_vec = model.encode(chunk.embed_text,          normalize_embeddings=True)
```

**这是最容易漏、后果最严重的一条。** 漏了会明显掉点，而且**排查时看不出任何报错**，只会觉得「怎么召回的都不对」。

**② 向量必须归一化**，配合 Milvus 的 `COSINE` 度量。不归一化会导致不同长度文本的相似度不可比。

**③ 模型与维度定死后不改。** 改了 = 8156 行全部重新编码 + 重建索引 + 查询侧同步改。

### 工程细节

- 批量：`embed.py` 用 `batch_size=16`（CPU）
- **分片**：每 1000 条落一个 `part-NNN.npy` + 同名 `.jsonl`。跑到一半断了不用从头再来
- **日志要开行缓冲**：`sys.stdout.reconfigure(line_buffering=True)`。重定向到文件时 stdout 默认块缓冲，会攒满 8 KB 才落盘——跑了 31 分钟，日志里一条进度都看不到。实测踩到，`embed.py` 与 `ingest.py` 都加了

### 实测耗时比方案预估慢一个量级

方案预估「bge-m3 CPU 约 20~50 条/秒，**3~7 分钟跑完，不是瓶颈**」。实测差了 5~10 倍：

| 跑次 | 条数 | 实编条数 | 耗时 | 折算 |
|---|---|---|---|---|
| 首轮全量 | 7949 | 7949 | 30.9 分钟 | 4.3 条/秒（`产出/日志/第7步-向量化-全量7949条.log`） |
| 扩充后 | 8156 | 6156（前 2000 条沿用未变分片） | 20.5 分钟 | 5.0 条/秒（`产出/日志/第7步-向量化-全量8156条.log`） |

原因是条文比预想的长，且 `embed_text` 还叠了制度名与条款号的上下文头。结论仍然成立——**不是瓶颈**，但排期时按**半小时**算，不是 3 分钟（全量重编 8156 条约 27 分钟）。

> **日志里的「条/秒」是「累计条数 ÷ 总耗时」**，把跳过的分片也算进了分子 —— 本轮头几片显示
> `18.2 条/秒` 就是这么来的（那 2000 条根本没编）。**看单条耗时别看这个数**，或者只拿
> 末行的累计值。这不是 bug，是显示口径；写进这里免得下次有人照抄 `18.2` 去估排期。

自检输出（`embed.py` 末尾自动跑）：

```
向量 (8156, 1024) 期望 (8156, 1024)
### 校验全过：8156 条 × 1024 维，范数 [1.0000, 1.0000]，clause_id 顺序一致
```

> **扩充语料后不要指望「只编新增的那几条」。** 分片是**按全量顺序**切的（每 1000 条一片），
> 新文件插在中间会让它之后的所有分片错位。`embed.py` 的跳过条件是 `if n == len(part)`
> ——**只看片长不看内容**，一个「长度相同但内容已经移位」的旧片会被**错误地跳过**，
> 而顺序校验是最后的兜底。安全做法：**把受影响的分片挪走再跑**（本轮的处置是把
> `part-002..007` 移到 `产出/_fetch/emb_old/`，保留内容未变的 `part-000/001`）。
> 挪是**可逆**的，删不是。

**顺序一致**是这里最要紧的一条：向量文件与 `clause_id` 一旦错位，入库后每条向量都挂在别人的条文上，**Milvus 不报错**，检索结果会变得「似是而非」。所以分片旁边必须配一份 `.jsonl` 记顺序。

## 第 8 步：入库 → Milvus

**进来什么**：8156 个向量 + 条文 + 元数据。
**做什么**：建 collection、建索引、批量写。
**出去什么**：`finance_clause` collection，8156 条。

### Schema

主键 `clause_id` VARCHAR(64)，向量 `embedding` FLOAT_VECTOR(1024)，两个文本字段 `text` / `embed_text`，其余是标量。完整定义见 [契约/DB.md](../契约/DB.md) §3。

### 索引

| 对象 | 类型 | 参数 |
|---|---|---|
| `embedding` | HNSW | M=16, efConstruction=200, **metric=COSINE** |
| `status` | INVERTED | — |
| `domain` | INVERTED | — |
| `effective_date` | INVERTED | — |

后三个是**时效性过滤的落点**，缺了索引 `filter=` 会退化成全表扫。

**不分区。** 8156 条这个量级，按 `domain` 分区没有检索收益，反而增加写入与维护复杂度。

### 写入流程

用 pymilvus 的 ORM，**每行一个字典**（`脚本/ingest.py`）：

```python
from pymilvus import Collection
coll = Collection("finance_clause", schema=build_schema(1024))
for i in range(0, len(rows), 500):
    coll.insert(rows[i:i + 500])        # rows 是 list[dict]，键就是字段名
coll.flush()
coll.create_index("embedding", {"index_type": "HNSW", "metric_type": "COSINE",
                                "params": {"M": 16, "efConstruction": 200}})
for f in ("status", "domain", "effective_date"):
    coll.create_index(f, {"index_type": "INVERTED"})     # 时效性过滤的落点
coll.load()
coll.query(expr="clause_id != ''", output_fields=["count(*)"])   # 期望 8156
```

**必须用行式字典，不能用列式 `list[list]`**（坑 #16）。pymilvus 对列式只比对字段**个数**、不比对字段**名**——`orm/schema.py` 的 `_check_data_schema_cnt` 只在 DataFrame 分支才查列名。列顺序写错会把整批行的字段静默串位，Milvus 一句错都不报。行式字典的键对不上会当场抛异常。

**服务端与客户端必须同为 2.5 线**（坑 #15）：`Milvus v2.5.27` + `pymilvus>=2.5,<2.6`。

### 入库前的三道闸门

`ingest.py` 不过就中止，不留半成品：

| 闸门 | 查什么 | 不过的后果 |
|---|---|---|
| 1 字节预检 | 每个 VARCHAR 按 **UTF-8 字节**比对 DB.md 的 `max_length` | `org` 曾写 128 而实测 174 字节，插到一半才炸 |
| 2 对齐预检 | chunk / 向量 / 向量 id 三者条数一致，且 `clause_id` 顺序一致 | 整批字段串位，检索结果似是而非 |
| 3 落库复核 | 插入后 `count(*)` | 批次丢了或重复入库，**不报错** |

实测通过：

```
闸门 1 过：14 个 VARCHAR 字段均在 DB.md 的 max_length 内（按 UTF-8 字节）
闸门 2 过：8156 条，向量与 chunk 的 clause_id 顺序一致
建表 finance_clause：21 个字段
已插入 8156 条并 flush
已建索引：HNSW(COSINE) + 3 个 INVERTED，并 load

落库 count(*) = 8156，期望 8156
### 三道闸门全过，知识库就位
```

**验什么**：`count(*)` **精确等于 8156**，不是「> 0」。出现 8100 或 8200 都说明有一批文件读失败或重复入库了。

这个数是**一对数**，只对一个不算过：**锚点 8036**（`_verify.py` 数出来的，SPEC §6 校验过）**+ 超长条二次切 120 = 入库 8156**。锚点数变了、或者差值不再是 120，都要查清楚是哪一步变的。

> **这几个数会随语料扩充而变，别背。** 改完语料跑 `python 脚本/_counts.py`，它一次报全
> （锚点数 / 二次切数 / 各字段空值 / 各轴分布），照着改文档。`脚本/ingest.py` 顶上的
> `EXPECT_ROWS` 也是这个数 —— 语料变了不改它，闸门 2 会直接拦下来（拦是对的，别去绕过它）。
> 散在六份文档里的硬编码数字不止一处，本轮实际漏改过，见 [契约/README.md](../契约/README.md) §6.1。

## 第 9 步：检索 → top-k 条文

**进来什么**：用户问题 + 筛选项。
**做什么**：混合检索 + RRF 融合 + rerank。
**出去什么**：top-k 条文（`ClauseBrief` 列表）。

```
query ──┬─→ bge-m3 编码（加前缀）─→ Milvus 向量检索 ─┐
        │                    （filter 先过滤）        ├─→ RRF ─→ rerank ─→ top-k
        └─→ jieba 分词 ──────→ BM25 关键词检索 ──────┘
```

向量检索管语义（「资本充足率要求」能命中「核心一级资本充足率不得低于」），BM25 管精确匹配（文号、专有名词、法规简称）。**RRF（Reciprocal Rank Fusion）** 按排名倒数加权融合两个列表，无需调权重。rerank 用 `bge-reranker` 对融合后的 top-N 精排到 top-k。

### 过滤是先过滤后检索

```python
res = client.search(
    collection_name="finance_clause",
    data=[query_vec],
    filter='status == "有效" and effective_date <= 20241019',   # ← 先过滤后检索
    limit=10,
    output_fields=["clause_id", "doc_title", "clause_no", "text", "source_url"],
)
```

**Milvus 的 `filter=` 是先过滤再检索，不是检索后再筛。** 写成「先 search top100，再在 Python 里过滤 `status`」，过滤后可能只剩几条，召回严重不足，**而且不报错**。

`output_fields` 要覆盖 `ClauseBrief` 的全部字段，缺字段就要回查 MySQL，多一次往返，影响 ≤2 秒指标。

**验什么**：50 题小评测集，top5 命中率 ≥ 80%。

## 第 10 步：生成 → 答案 + 溯源

**进来什么**：top-k 条文 + 原问题。
**做什么**：拼 Prompt、调 LLM、流式吐字。
**出去什么**：SSE 事件流。

### Prompt 与拒答

检索到的条文拼进 Prompt，要求 LLM **只依据给定条文回答**。检索不到相关内容时**拒答**而不是编——这是差异化要求的一部分。

### 流式事件

四类事件，顺序固定：

```
delta* → sources → score → done
```

| 事件 | `data` |
|---|---|
| `delta` | `{"text": "商业银行"}` |
| `sources` | `{"sources": [ClauseBrief...]}` |
| `score` | `{"score": 0.87}` |
| `done` | `{"qa_id": 10241, "elapsed_ms": 1360}` |

前端**收到 `sources` 就渲染卡片，不等 `done`**——用户看着答案一个字一个字出来的时候，引用卡片已经在旁边了。这是「答案溯源」体验的关键。

**验什么**：`elapsed_ms` ≤ 2000；拒答场景 `sources` 为空数组。

### 数字是一对，不是一个

**8036 是「锚点数」，8156 是「入库行数」**，差 120，全部来自超长条二次切：

| 来源 | 影响 |
|---|---|
| 超长条（> 1000 字）二次切 | 一条变两三条，片间重叠 80 字 |
| 无条款结构走兜底（400 字一片） | 本语料用不到——159 份全落进三种锚点体例 |

**两个数都要对得上**：`_verify.py` 出 8036，`pipeline.py --all` 出 8156。只对一个不算过。
**这两个数不是常量**：语料一变就跟着变（本轮 7830/7949 → 8036/8156）。改完语料先跑
`python 脚本/_counts.py` 报数，再改散在六份契约文档里的硬编码值。

切分器与 `_verify.py` **复用同一份锚点逻辑**（`脚本/_kb.py`）。这件事必须共用一份——分开写的后果是「数出来一个数、切出来另一个数」，而且查不出是哪边错了。本项目真踩到了：清洗的硬换行合并规则吃掉了 41 个行首锚点（`SZSE-001` 少 25 条、`PBC-074` 少 16 条）。现在 `pipeline.py` 跑的时候会自己核对，对不上直接中止。

## 十八个坑

技术方案列了 8 个，本项目实测又踩到 10 个（#9~#18）。

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 按固定字数切分 | 条文被切断，溯源失效 | 按「第X条」切，超长条再二次切 |
| 2 | 忘记 query 指令前缀 | 检索明显掉点，且查不出原因 | query 加前缀，passage 不加 |

| **9** | **跨行断句被当成锚点** | 凭空多算条数，连续性断裂 | `REF_TAIL`：锚点前行以 `》` 结尾则跳过。修正 `CSRC-020`/`PBC-057` |
