**2026-10-27 由 P2 记录。这是一条红线事项，不自行处置，需要团队裁决。**

技术方案 §1.4 定的红线里有两条与本文相关：

> 遵守 `robots.txt`，请求频率 ≤ 1 次/秒，正常 User-Agent；
> 逐条记录 `source_url` 与采集时间。

结论先说：**我们引用的 140 条 `source_url` 里，74 条（52.9%）落在明确 `Disallow: /` 的域名上**，
其中 `flk.npc.gov.cn` 的 robots.txt 更是**明文禁止自动化采集**。而本轮做日期查证的子代理

## 4. 我们不知道的一件事，本身就是问题

**语料那 158 份原始文件是怎么下载的，仓库里没有任何记录。** 找过：

| 找的地方 | 结果 |
|---|---|
| `脚本/` 全部 12 个脚本 | 当时**没有**采集/抓取脚本。唯二的采集相关脚本 `_fetch_nfra016.py`、`_merge_urls.py`/`_pubdate_fix.py` 都是本轮才写的，**只对新增那 1 份与原 158 份的 URL 元数据**起作用，不解释 158 份原件怎么来的 |
| `数据源/` 8 个编号目录 | 只有原始文件，没有采集说明 |
| `产出/日志/` 7 份日志 | 全是切分/向量化/入库/装依赖，**没有一份与采集有关** |

所以无法断言语料本身是否经由爬虫获得。若当初是**人在浏览器里一篇篇下载**的，
robots.txt（约束自动化代理）**不适用**，语料无问题；但这一点**拿不出证据**。

> **这一条从今天起不再是全库性的缺口了**：`NFRA-016` 的采集全程有记录（§4.1）。
> 但**原 158 份仍然没有** —— 有 1 份的记录，不等于补上了前 158 份的账。

顺带：技术方案 §1.4 要求「逐条记录 `source_url` **与采集时间**」。`fetched_at` 字段有，
**159/159 非空**；但**采集方式（人 / 爬虫 / 频率）没有记在任何地方**，
所以红线里的「请求频率 ≤ 1 次/秒」这一条**无法自证**——`NFRA-016` 除外，
它是单次请求，天然满足（§4.1）。

## 4.1 `NFRA-016` 是唯一一份**采集过程有全程记录**的件（2026-10-27）

上面 §4 说「语料 158 份是怎么下来的，仓库里没有任何记录」。**`NFRA-016` 是例外，
而且是有意做成例外的** —— 补语料的同时把 §4 那个缺口在**至少一份**上堵掉：

| 项 | 记录 |
|---|---|
| 来源页 | `https://www.gov.cn/zhengce/202311/content_6913410.htm`（中国政府网 · 部门规章频道） |
| 采集时间 | `20261027`（写进元数据 `fetched_at`） |
| robots.txt | `www.gov.cn` → `User-agent: * / Allow: /1` + `Disallow:/2016*/`；本页路径 `/zhengce/202311/…` **不在禁止列** |
| 请求次数 | **1 次**。页面 HTML 落在 `产出/_fetch/gov1.html`，脚本**有缓存就直接用**，不重复打站（`_fetch_nfra016.py` 的 `fetch()`） |
| User-Agent | `Mozilla/5.0 (compatible; RAG-coursework/1.0)` —— 正常 UA，非空、非伪装浏览器 |
| **未访问** | `pbc.gov.cn` / `flk.npc.gov.cn` 一次都没碰（两者 `Disallow: /`，§6 定的规矩） |
| 采集脚本 | `脚本/_fetch_nfra016.py`，**默认 dry-run，加 `--write` 才落盘** |

**它是「转」的不是「下载的」，这一点必须写明。** gov.cn 该页只把**正文内联在 HTML 里**，
挂的 25 个 `.docx/.doc` 全是附件 1–25，**没有「办法正文」的单件原件**。所以脚本把页内正文
原样转成 `.docx` 落进 `数据源/`。**与其余 158 份（人工下载的原件）不是同一类来源**，
元数据的 `note` 里已注明，[契约/README.md](../契约/README.md) §4 #15 单列了一条。

**三条刻意的取舍**（是取舍，不是漏）：

1. **25 个附件全部不纳入。** 附件是分册的技术规则（附件 3 单份就顶得上正文），
   全收会把 1 份变成 26 份，而全库附录级文书本来也只有 3 份。正文里对附件的援引
   （「（二十五）附件25：外部评级使用规范。」）**原样保留，不删**。
2. **页尾「附件下载」清单剔除。** 那是页面渲染块不是正文；判据是「以 `.docx`/`.doc`/`.pdf`
   后缀结尾」，正文援引条目以「。」收尾，不会带后缀。
3. **正文中间那张表就地摊平成文本行**，不做成真 docx 表格 —— `_kb.read_pages` 读 docx 时
   会把表格单元格追加到**全部段落之后**，做成真表格会让它脱离所在的那一条。

**这份件不解决 §6 的裁决**：74 条禁止域 URL 一条没动，`NFRA-016` 只是**新加的第 141 条**
落在一个允许域上。它证明的是「合规采集是能做到的、且有留痕」，不是「原来的问题已经处理」。

## 5. 一处与白名单不符的 URL

`SPC-001` 的 `source_url` 是 `https://www.spp.gov.cn/…`，而 `脚本/_merge_urls.py` 的
`OK_HOSTS` 白名单**不含 `spp.gov.cn`**。它能进表是因为它属于最早那 20 条「正文页脚自带」的 URL——
那批**从未过白名单校验**（白名单是为后 120 条联网查证设的）。该站无 robots.txt，不受限，
所以这不是合规问题，是**校验口径不一致**：重跑 `_merge_urls.py` 会把这条判为「不在白名单」。

## 7. 这件事**不需要**做的

- **不需要**因为 robots 就怀疑语料内容质量。74 条 URL 指向的页面都是**版本已核实一致**的官方页，
  与「§8.3 官方页存在 ≠ 可填」是两个独立问题。
- **不需要**把已入库的语料删掉重来。语料是离线文件，与"是否曾被程序化获取"无关；
  要改的是**引用方式与后续访问方式**。
